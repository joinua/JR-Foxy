# TikTok: перевірка RSS і сповіщення

Бот читає налаштовану RSS/Atom-стрічку. Він не перевіряє профіль TikTok напряму: якщо RSS не містить відео, бот не може оголосити про нього. Видалення відео TikTok або затримка RSS не означають зупинку планувальника.

## Команди й налаштування

| Команда | Де і кому доступна | Дія |
| --- | --- | --- |
| `/tiktok_status` | Приват або адмін-чат, рівень 3+ | Читає налаштування, останній результат, кількість відправлених/необроблених відео, найновішу дату публікації в останній перевіреній стрічці та найближчу активну задачу. Час за Києвом. RSS не запитує, повідомлення в головний чат не надсилає. |
| `/tiktok_check` | Приват або адмін-чат, рівень 3+ | Виконує перевірку і може опублікувати нові відео, навіть коли автоматичні сповіщення вимкнені. Відповідь пояснює ручний режим. |
| `/tiktok_enable`, `/tiktok_disable` | Приват, рівень 4+ | Вмикає/вимикає автоматичну публікацію. Увімкнення відновлює відсутню задачу; чинний розклад зберігається. |
| `/tiktok_set_thread` | Потрібна тема головного чату, рівень 4+ | Зберігає тему для майбутніх публікацій. |

Значення `tiktok_notify_enabled`, `tiktok_rss_url` і `tiktok_thread_id` у `chat_settings` мають пріоритет над відповідними змінними середовища. Порожні RSS/тема використовують значення середовища. `tiktok_notify_enabled='1'` вмикає публікацію, інші збережені значення вимикають її. Без теми повідомлення йдуть у загальний головний чат. Некоректна тема є явною помилкою, а не приводом змінити місце публікації.

## Читання і доставка

- HTTP-запит має загальний ліміт 20 с, підключення/читання — по 10 с. Максимум 2 MiB та 200 записів у відповіді.
- Порожня коректна стрічка, некоректний XML, HTTP-помилка, таймаут, помилка Telegram і помилка SQLite мають різні результати. Журнал і збережений діагностичний стан не містять RSS URL або сирих відповідей сервісу.
- Обробляються всі записи незалежно від розташування закріпленого відео. Невідомі раніше записи відправляються за датою, максимум по 5 за перевірку. Для недатованих нових записів використовується початок черги; однакові дати впорядковуються за ID.
- Для стандартного TikTok-посилання ідентичність визначається числовим ID відео. Зміна RSS GUID чи порядку записів не спричиняє повторного повідомлення. Для інших посилань використовується GUID/ID або саме посилання.
- Після підтвердженої відправки запис зберігається в SQLite. Часткова помилка залишає невідправлені записи для наступної спроби. Помилка окремого повідомлення в адмін-чат не скасовує успішну публікацію в головний чат.
- Ручна й автоматична перевірки захищені спільним блокуванням у межах одного процесу бота. Паралельний виклик повертає `busy`.

Це не гарантія доставки «рівно один раз»: якщо Telegram прийняв повідомлення, але відповідь загубилася, процес завершився до запису історії або SQLite не зберегла результат, повторна спроба може створити дублікат. Два одночасні екземпляри бота не підтримуються. Відео, яке зникло з RSS між перевірками, відновити через цей механізм неможливо.

## Початковий запуск і міграція

`init_db()` додає таблиці `tiktok_feed_state` і `tiktok_seen_videos`, не видаляючи існуючі дані. Останній результат зберігається в `chat_settings.tiktok_check_state`. Старий `tiktok_last_video_id` продовжує оновлюватися для сумісності.

Під час першої успішної непорожньої перевірки нового RSS URL:

1. Якщо старий `tiktok_last_video_id` знайдено у стрічці і він має дату, записи з такою самою/старішою датою та недатовані записи позначаються як уже оброблені. Новіші записи можуть бути опубліковані одразу.
2. Якщо контрольного запису або його дати немає, вся поточна стрічка стає початковим списком без розсилки. Це запобігає масовій публікації історичних відео, але нові записи, які вже були у цьому першому списку, також не оголошуються. Результат — `initialized`.
3. Порожня або помилкова відповідь не фіксує початковий список.

## Планувальник

Звичайний інтервал задає `TIKTOK_CHECK_INTERVAL_SECONDS` (типово 3600 с після завершення перевірки). Перезапуск зберігає наявну задачу і її строк; якщо задачі немає, створює її на найближчий цикл планувальника.

Після помилки RSS/Telegram/SQLite/внутрішньої помилки наступна перевірка планується через `min(інтервал, 300)` с. Якщо залишилися відео понад ліміт або перевірка вже зайнята — через `min(інтервал, 60)` с. Результати `disabled`, `rss_missing`, `empty_feed`, `initialized` та `no_updates` використовують звичайний інтервал.

Операція створення наступної задачі атомарна і повторно використовує наявну pending-задачу. Періодичне відновлення планувальника відтворює відсутню задачу, зокрема після вичерпання спроб. Помилка БД поза обробником не завершує весь цикл планувальника. Окрема завершена задача `done` означає завершення спроби; результат RSS/доставки треба дивитися через `/tiktok_status` та журнал.

## Перевірка й оновлення

Автоматичні тести використовують тимчасову SQLite, локальний HTTP-сервер і підставний Telegram-клієнт:

```bash
python -m unittest discover -s tests -p 'test_tiktok.py' -v
python -m unittest discover -s tests -v
```

Перед production-оновленням потрібна актуальна перевірена копія бази та конфігурації. Розгортання виконується тільки штатним `.github/workflows/release-deploy.yml` з обліковим записом `deploy`. Після перенесення VPS треба перевірити відповідність `DEPLOY_HOST` і довіреного SSH host key новому серверу, не вимикаючи перевірку host key.

Після погодженого розгортання:

1. Виконати `/tiktok_status` у приваті: перевірити, що сповіщення ввімкнені, RSS налаштовано, тема відповідає очікуваній, є активна задача.
2. Після строку цієї задачі повторити `/tiktok_status`: час перевірки має оновитися, наступна задача — існувати. Це перевіряє автоматичний запуск без примусової публікації.
3. Перевірити доставку на наступному справжньому відео, яке присутнє в RSS: повідомлення має з'явитися в потрібній темі; наступна перевірка не має створити повтор.

`/tiktok_check` — не діагностика без побічних дій: вона може одразу опублікувати відео. Після відновлення старішої резервної копії SQLite історія доставки також повертається до дати цієї копії, тому можливі повторні оголошення.
